FOUNDATIONS

Operating systems, decoded.

01 · Process vs thread

A process is a running program with its own resources. A thread is an execution path within a process; threads in one process share memory and other resources.

02 · Thread lifecycle

Threads are created, run, may wait, and eventually finish. The exact state transitions depend on the runtime and the operating system.

03 · Multithreading and concurrency

Concurrency means tasks make progress over overlapping periods. Parallelism means tasks execute simultaneously on separate computing resources.

04 · Shared resources

Threads can access the same data. Coordinating updates prevents inconsistent state and unintended interference.

05 · Race conditions

When a result depends on the timing or interleaving of operations, access to shared state may produce unpredictable results.

06 · Critical section & mutual exclusion

A critical section accesses shared resources that must be protected. Mutual exclusion allows only one participant into that section at a time.

07 · Mutex synchronization

A mutex is an ownership lock used to serialize entry to a critical section. Other threads wait until the owner releases the lock.

08 · Producer–consumer coordination

Producers insert items into a shared bounded buffer, while consumers remove them. Full and empty conditions require coordination.

Recommended learning path

  1. Start with Thread Creation. Watch individual workers start, report progress, and finish.
  2. Explore the Race Condition. Compare unsafe and protected reads/writes.
  3. Step into Mutex Synchronization. Observe waiting, acquisition, and release.
  4. Finish with Producer–Consumer. Watch a finite shared buffer fill and empty.
  5. Review Linux Observation. Learn how to inspect processes on an actual Linux machine.

System design & frontend boundaries

Real browser workers

Thread Creation uses actual JavaScript Web Workers for separate worker execution and message-passing.

Educational OS simulations

Race Condition, Mutex, Producer–Consumer, and process states use explicit modeled events. They illustrate correct concepts but are not the Linux scheduler or C++ threading engine.

Linux output is illustrative

Terminal data is a clearly labeled teaching example. Browser API values come from the local browser when available.

Persistence & safety

Completed runs are saved only in your browser via localStorage. The app does not execute arbitrary user code, send network requests, or require a database.

Frequently asked questions

Is a browser Web Worker the same thing as a C++ / POSIX thread?

No. A Web Worker runs JavaScript in a separate browser execution context. It is a practical browser-native concurrency mechanism, but not direct execution of the proposal’s C++ or POSIX thread programs.

Why can the unsynchronized shared counter lose updates?

Because read–modify–write contains several operations. If multiple threads read an old value before any write, later writes overwrite updates that should have accumulated.

Does the mutex visualization reflect actual kernel scheduling?

No. It is a simulated FIFO mutex model using application-recorded events; the proposal specifically describes simplified thread-state visualizations rather than exact scheduler state.

Can this frontend execute Linux ps or top commands?

No. A normal static website cannot inspect your computer's OS process list or start a local C++ binary. Linux Observation instead demonstrates representative command output and available browser information.

Where are my results kept?

In the current browser's local storage, without an account or database. Export JSON/CSV files from Run History before clearing your browser data if you want a portable copy.
